# Onyx generated-artifact authorization gap

This is a confirmed authorization boundary failure with conditional P1 impact. Any authenticated user who obtained a generated artifact's file ID could pass the reviewed download check.

The reviewed revision is [`c424edb5118743443b3438c7e4895d0c962a794a`](https://github.com/onyx-dot-app/onyx/commit/c424edb5118743443b3438c7e4895d0c962a794a).

The evidence includes a pinned source trace and constructed K claims. The retained audit did not complete a two-user runtime reproduction or establish an independent file-ID disclosure path.

## 1. System boundary

Onyx stores files generated by image tools and Python execution in a shared FileStore. The application returns links that resolve through an authenticated download endpoint. Other file categories use ownership, shared-chat access, persona access, or document ACLs to decide whether a user may read the bytes.

Generated images and Python-tool outputs shared the `CHAT_IMAGE_GEN` origin. These artifacts can contain reports, data transformations, images, and files derived from private chat or uploaded context.

Every generated file had to remain an authority-bearing object. A download had to resolve the requesting user to an owner or an explicit sharing rule. A file ID or storage category could identify the object but could not grant access by itself.

## 2. Root cause

The download endpoint delegated its security decision to [`user_can_access_chat_file`](https://github.com/onyx-dot-app/onyx/blob/c424edb5118743443b3438c7e4895d0c962a794a/backend/onyx/access/access.py#L213-L273). Most branches linked the requested file to user or document context.

The `CHAT_IMAGE_GEN` branch used a different rule. If a matching FileStore record existed with that origin, the function returned access without checking the requesting user, chat, session, tool call, persona, or document ACL.

The [authenticated download endpoint](https://github.com/onyx-dot-app/onyx/blob/c424edb5118743443b3438c7e4895d0c962a794a/backend/onyx/server/query_and_chat/chat_backend.py#L893-L930) streamed the stored bytes after that function returned true. Basic authenticated access was therefore enough once the caller supplied a matching file ID.

The origin covered more than images. The [Python tool](https://github.com/onyx-dot-app/onyx/blob/c424edb5118743443b3438c7e4895d0c962a794a/backend/onyx/tools/tool_implementations/python/python_tool.py#L304-L315) stored code-execution outputs with the same value before returning download links.

The boundary failure was an authority substitution. The implementation used a storage-origin label where the security model required a user or sharing relationship.

## 3. Reachability and impact

An attacker needed a valid authenticated account and the target file ID. The source trace established neither predictable IDs nor a second endpoint that exposed another user's identifier. That missing prerequisite makes the P1 impact conditional.

If the attacker obtains the ID, the authorization function has no remaining ownership check. The endpoint can return artifacts produced in another user's chat or tool session. Those files may contain transformed uploads, generated reports, tabular exports, images, or model-derived private content.

The confirmed defect is cross-user authorization failure. The worst-case impact is disclosure of sensitive generated content. The report does not claim that arbitrary file discovery was proven.

## 4. How the KIT found it

The KIT classified FileStore records as security objects before following individual branches. Public product behavior established that generated files can carry user data and that main-application access controls govern downloads.

The intent ledger produced three linked obligations:

1. Generated output must attach to its producing user, chat, session, or job.
2. A download must resolve that attachment before returning bytes.
3. Revoked, stale, or unlinked identifiers must not grant access.

The K claims modeled attachment and download separately. Claims C3 and C4 required generated output to stay inside its authority context. The file-specific claim required a concrete link whose ACL allowed the requesting user.

The source branch for `CHAT_IMAGE_GEN` could not satisfy that precondition. It reached the byte-return sink using only the file record and origin. Comparing it with the owner, shared-chat, persona, and document branches showed exactly where authority context disappeared.

The K package was constructed and was not machine-checked. The proof obstacle was still useful because it converted a broad cross-user isolation requirement into one missing relation at the download decision.

## 5. Evidence status

The retained audit traced generated Python outputs into FileStore, followed the returned link to the common download endpoint, and inspected every authorization branch. The origin-only branch was a direct source-level allow decision.

No two-user local deployment test was completed. The audit also did not show how a second user would learn the target file ID. The report therefore separates the confirmed authorization defect from its conditional P1 impact.

The evidence supports remediation and a focused regression test. It does not support a claim of demonstrated mass file enumeration or current-release exposure.

## 6. Repair direction and limits

Onyx should persist owner, chat, session, tool-call, or job linkage before making a generated file downloadable. The authorization function can then use the same explicit relationship model as other private files.

If storage must occur before the linking record exists, the interim state should deny downloads. A pending-private record preserves ordering without making an entire origin class readable by every authenticated user.

A two-user regression test should create a generated artifact as user A, request it as user B, and expect the same denial behavior used for other private chat files. Tests should cover both image generation and Python-tool output.

This analysis covers the pinned revision and makes no claim about current Onyx releases.
